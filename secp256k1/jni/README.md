# secp256k1 JNI shim on upstream libsecp256k1

`secp256k1/` is now an **unmodified** copy of upstream
[bitcoin-core/secp256k1](https://github.com/bitcoin-core/secp256k1) **v0.8.0**
(`v0.8.0.tar.gz`, sha256
`eb52b0e9239dff7dc26be5f9623567141b8720ec47da29eb3c1e0a660d17c8bb`, with only
`.github/` and `.cirrus.yml` dropped). Everything rskj-specific lives in this
directory:

| file | role |
|---|---|
| `org_bitcoin_NativeSecp256k1.c` | the JNI shim, for both `org.bitcoin.NativeSecp256k1` and `org.bitcoin.Secp256k1Context` |
| `org_bitcoin_*.h` | generated by `javac -h` (gitignored; `../../build_secp256k1.sh` regenerates them) |
| `tools/` | the micro-benchmark and the old-vs-new conformance harness used to validate the port |

## Why

The previous `secp256k1/` was a fork of upstream **0.1** last synced in 2019,
configured without the GLV endomorphism (still patent-gated then), without the
safegcd modular inverse (2021) and without assembly. Measured on the rskj
ecrecover precompile with the same input (Apple M-series, JDK 17):

| | per ecrecover | ecdsa replay, ms per 25M-gas block |
|---|---|---|
| old fork (0.1) | 29.6 µs | 232.3 (p95 250.9) |
| upstream 0.8.0, this shim | 12.1 µs | 96.6 (p95 107.8) |
| rustock (libsecp256k1 0.6 via the `secp256k1` crate) | 11.5 µs | 84.7 (p95 86.6) |

Replay numbers are the clients-lab `ecdsa` sample (207 blocks, 203 at ≥90%
gas) replayed back to back in the same Docker arm64 container limits on
2026-10-30, all 207 block hashes matching the reference in every run.

The Java layers above the JNI call cost under 1 µs, so the whole gap was the
library build.

## How the shim is built

One translation unit: the shim `#include`s `../src/secp256k1.c`, exactly as
upstream's own `tests.c` and `bench.c` do, and is compiled together with the two
precomputed-table sources (`src/precomputed_ecmult.c`,
`src/precomputed_ecmult_gen.c`). No autotools, no CMake, no patch to upstream.
`build_secp256k1.sh` at the repo root does it for macOS (clang, arm64 and
x86_64) and Linux (gcc in Docker buildx, amd64 with `USE_ASM_X86_64`, arm64) and
stages the binaries under `src/main/resources/org/bitcoin/native/`.

Compile-time configuration is upstream's defaults except
`ECMULT_WINDOW_SIZE=20` (since native 1.6.0, see below): `COMB_BLOCKS=11`/
`COMB_TEETH=6`, modules `recovery` and `ecdh`, `-O3`. The script takes
`SECP_DEFS`, `SECP_CFLAGS`, `SECP_X86_ASM=0` and `SECP_RES` overrides for
variant builds; a window above 15 regenerates `precomputed_ecmult.c` in the
work copy with upstream's `precompute_ecmult`, the vendored tree stays untouched.

## Build-time tuning (2026-11-05)

Recovery is one variable-time `secp256k1_ecmult` (Strauss wNAF over the
`ECMULT_WINDOW_SIZE` table of G multiples) plus two modular inverses, so the
window size and the field-code flags were the candidates. Measured as
`PrecompiledContracts.ECRecover.execute` with `tools/Bench.java ecrecover`
(50k iterations after 20k warm-up, three JVM runs, median) against the rskj
jar `fa5733f8`; arm64 Linux in an `eclipse-temurin:17-jdk` container on the
same Mac, amd64 in the same image under emulation (its absolute numbers are
indicative only, the ranking is what counts).

| variant | Mac M4 Max arm64 | Linux arm64 | Linux amd64 (emulated) | binary size |
|---|---|---|---|---|
| `ECMULT_WINDOW_SIZE=15`, gcc defaults (1.5.0) | 12.36 µs | 12.49 µs | 19.34 µs | 1.2 MB |
| `ECMULT_WINDOW_SIZE=18` | 12.50 µs | 12.50 µs | 19.15 µs | 8.6 MB |
| **`ECMULT_WINDOW_SIZE=20` (1.6.0)** | **11.87 µs (−4.0%)** | **11.86 µs (−5.0%)** | **18.31 µs (−5.3%)** | 34 MB |
| `ECMULT_WINDOW_SIZE=22` | does not build | does not build | not tried | (256 MB) |
| w15 + `-march=x86-64-v3`, asm | | | 21.59 µs | |
| w15 + `-march=x86-64-v3`, no asm | | | 20.36 µs | |
| w15 + `-march=x86-64-v2`, asm | | | 19.43 µs | |
| w15 + `-march=x86-64-v2`, no asm | | | 19.29 µs | |
| w15, no `USE_ASM_X86_64` | | | 19.08 µs | |

- The window is the only knob that moves the needle: w=20 saves about 0.5 µs
  per `ecrecover`, roughly 3.7 ms per 25M-gas ecdsa block (7,350 calls).
  w=18 is noise. The price is two 16 MB tables (32 MB per binary, four
  binaries in the jar, 64 MB resident per JVM that loads it).
- w=22 (308 MB of generated C) hits clang's source-location limit on macOS
  and OOMs gcc inside the 31 GB Docker VM on Linux; it would be a 256 MB
  binary anyway.
- `-march=x86-64-v2`/`v3` and dropping the x86_64 scalar asm are all within
  noise or worse under emulation (v3 is slower there because AVX2 is emulated
  poorly), so amd64 keeps the baseline flags: generic x86-64 with
  `USE_ASM_X86_64`. Re-measure the march variants on the real Boton CPUs
  before concluding anything about them.
- `tools/Conform.java` output (1,752 lines) is byte-identical for every
  variant above on all three platforms, including the shipped w=20 binaries.

## What changed in the port

Public API renames only; the Java-visible contract (buffer layouts, the
`byte[][] {payload, status}` return shape, status codes) is unchanged:

- `secp256k1_ec_privkey_{negate,tweak_add,tweak_mul}` →
  `secp256k1_ec_seckey_{negate,tweak_add,tweak_mul}` (same semantics; the old
  names were removed upstream in 0.8).
- `secp256k1_context_create(SIGN | VERIFY)` → `SECP256K1_CONTEXT_NONE` (the
  flags have been no-ops since 0.3; every context can sign and verify).
- `secp256k1_ecdsa_recover_is_infinity`, which the fork had added **inside** the
  library, is reimplemented in the shim with the library's internal
  scalar/group functions (available because of the single-TU build). It mirrors
  upstream's static `secp256k1_ecdsa_sig_recover` step by step and keeps the
  fork's status codes (`-1` parse, `-2` r=0, `-3` s=0, `-4` r+n overflow, `-5`
  not on curve, `1` infinity, `0` regular point), which
  `NativeSecp256k1.isInfinity` maps to exceptions and rskj's
  `Secp256k1ServiceNative` uses to return the zero key for the infinity case.

## Validation

`tools/Conform.java` drives every JNI method (sign DER and compact, verify,
pubkey create/parse/negate/tweak/add, ECDH, recovery with all four recids, the
infinity query) over 200 random keys, 300 junk signatures (including r=0, s=0
and r≥n), 50 **constructed point-at-infinity** signatures (R = kG, z = s·k mod
n) and the clients-lab dummy signature, printing every output in hex. Its
1,752 output lines are byte-identical between the old `1.4.0-SNAPSHOT` jar and
the new binaries on macOS arm64, Linux arm64 and Linux amd64.

Not preserved: nothing functional. Error *paths* that the old library reached
through different internal checks now come from upstream's argument checks,
which return the same 0/failed status to Java.
